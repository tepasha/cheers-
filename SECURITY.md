# Безпека

## Модель

| Шар | Що захищає | Де |
|---|---|---|
| **Автентифікація** | Вхід за email + пароль (Firebase Auth), підтвердження email, відновлення пароля, видалення акаунта | `src/services/authService.ts` |
| **Правила Firestore** | Єдина реальна межа доступу: хто що може читати й писати | `firestore.rules` |
| **Шифрування чатів** | Тіла повідомлень у Firestore лише як шифротекст (AES-GCM 256) | `src/services/cryptoService.ts` |
| **Шифрування кешу на пристрої** | Redux-стор шифрується ключем із Keychain/Keystore | `src/store/secureStorage.ts` |

### Що гарантують правила

* Усе, крім запису приватних даних, вимагає **підтвердженого email** (`email_verified`).
* Писати можна лише від власного імені: `senderId`, `userId`, `creatorId`, `reporterId` завжди звіряються з `request.auth.uid`.
* **Email, дата народження, XP** лежать у `users/{uid}/private/*`: їх читає лише власник. Публічний профіль не містить email, а координати округлюються до сітки ~20 м (див. нижче про наслідки).
* **Чат** доступний лише учасникам (`members`). Повідомлення **незмінні**: ні редагувати, ні видаляти. Id особистого чату виводиться з двох uid, тому зайняти чужий id неможливо. Склад групи змінює лише її творець.
* **Столики**: приєднатися можна один раз і лише на вільне місце; чужий столик змінити не можна.
* **Зустрічі**: учасник змінює тільки власний запис у `participants`; роль `host` собі призначити не може.
* **Відповідь на пропозицію зустрічі** — це окреме повідомлення `proposal_response` з id `resp_<id пропозиції>`, бо самі повідомлення незмінні. Правила пускають лише того, хто пропозицію *отримав* (автор не може прийняти власну), і лише раз: другий документ з таким id створити неможливо. Статус пропозиції обчислюється з цих відповідей в обох співрозмовників.
* **Місце, адреса й час пропозиції шифруються** так само, як текст повідомлення (поле `proposalCipher`); відкритий текст у `proposalData` правила відхиляють. Статус у шифрований блок не входить: він виводиться з відповідей.
* **Скарги**: створювати можна, читати назад ні (модератори читають через Admin SDK).
* **Блокування діє на сервері.** Список `users/{uid}/blocks/*` бачить лише власник; заблокований не може його прочитати чи дізнатися про блок. Якщо Боб заблокував Алісу, правила не дозволяють Алісі:
  * створити з Бобом особистий чат і писати йому (у наявний чат теж: історія лишається читабельною, нові повідомлення відхиляються);
  * зайняти місце за столиком Боба та приєднатися до його зустрічі;
  * відкрити його профіль за id;
  * створити групу з Бобом чи додати його до групи (групи обмежено 10 учасниками, щоб правила могли перевірити кожного, бо Firestore дозволяє 10 звернень до документів на запит).
  Боб, навпаки, може писати Алісі. Блок живе в хмарі й синхронізується між пристроями; розблокування також.
* **Спільні дані типізовані.** Столики, зустрічі, чати й повідомлення читає кожен клієнт, тож для кожного поля правила перевіряють тип і розмір. Учасники чату — різні рядки; новий учасник групи дописується лише в кінець списку, тому заблокований не сховається за переставленим або подвоєним записом. Час повідомлення (`createdAt`) приймається лише серверний (`request.time`): він упорядковує розмову, тож ні збитий годинник телефона, ні підроблене значення не переставлять і не зламають історію. Хост столика може лише продовжити, закрити чи змінити опис; хто сидить за столом, змінюють самі гості.
* **Чого правила перевірити не можуть** (окремі записи мапи `participants` у зустрічі, окремі елементи списків) застосунок перевіряє під час читання (`src/logic/cloudData.ts`): документ, що не відповідає формі, пропускається, а не валить стрічку. Колбеки слухачів Firestore обгорнуті так, що помилка в одному знімку лише пропускає його; кореневий `ErrorBoundary` показує екран «Щось пішло не так» замість закриття застосунку.
* Усі інші шляхи закриті.

### Чого вони не роблять (чесні обмеження)

* **Формат шифротексту `enc:v2` (HKDF-SHA256), `enc:v1` (PBKDF2) лише читається.** Вхід деривації не пароль, а стала плюс публічний id чату, тож розтягування PBKDF2 нічого не захищало, а коштувало 10 000 хешів на чат у чистому JS на Hermes. HKDF дає ключ тієї ж стійкості двома викликами HMAC. Це не підвищення безпеки (див. наступний пункт). Застосунки зі старим кодом не прочитають нові повідомлення `v2`, тому оновлюйтесь разом. Швидкодію на реальному пристрої я не вимірював.
* **Це не наскрізне шифрування між користувачами.** Ключ кімнати виводиться зі сталої в застосунку та id чату. Правила не пускають сторонніх до шифротексту, а шифрування захищає дані «у спокої» в сховищі, але хто має збірку застосунку **і** доступ до бази, може розшифрувати. Справжнє E2EE потребує обміну ключами між користувачами (наприклад X25519), це окрема робота.
* **Немає обмеження частоти запитів.** Правила не вміють rate limit. Увімкніть **Firebase App Check** (Play Integrity / App Attest) і квоти в консолі.
* **Повідомлення залишаються після видалення акаунта** (як шифротекст, для співрозмовників).
* Кількість учасників зустрічі (`maxParticipants`) перевіряє лише клієнт.
* **Життєвий цикл.** Столик живе 4 години: правила не приймають `expiresAt` далі ніж на 4 год 5 хв уперед. Автор може відновити столик ще на 4 години (так само, як і створити новий). Обмеження частоти створення правила дати не можуть, тож проти спаму потрібні App Check та серверні квоти. Зустріч зникає зі списків через 24 години після початку (`endsAt`, не далі ніж на 90 днів планування). Архів зустрічей лишається ще 30 днів і видаляється щогодинною Cloud Function `cleanupExpiredContent` (потрібен Cloud Scheduler, тариф Blaze). Числа задані в `src/logic/lifecycle.ts` і `functions/src/lifecycle.ts`, тест вимагає їхнього збігу. Правила не вміють видаляти за часом, тому без розгорнутої функції прострочені документи накопичуються, але клієнти їх не читають (запит фільтрує за `expiresAt` / `endsAt`).
* **Публічне місцезнаходження: сітка 0,0002° (приблизно 22 м на північ-південь, 14 м на схід-захід).** Так вирішено для «людей поруч» (радіус 3 км, до 50 профілів). Це точність до будівлі, а правила не вміють обмежувати читання за відстанню: будь-який підтверджений акаунт може запитати geohash-діапазон будь-де й побачити людей на цій сітці, а кількома запитами з різних точок можна уточнювати положення. Для застосунку про знайомства з незнайомцями це реальний ризик переслідування, тож його треба розуміти перед релізом. Зменшити ризик без втрати функції можна, змінивши сталу `PUBLIC_COORD_PRECISION` у `src/logic/privacy.ts` (наприклад, 1000 дає сітку ~100 м, 100 дає ~1 км); решта коду від неї не залежить. Відповідно оновлені політика конфіденційності та декларація даних у `docs/store/` (точне місцезнаходження).
* **Присутність.** Відкритий застосунок раз на 10 хвилин записує `lastSeenAt` у публічний профіль; профіль, який не заходив понад тиждень, показується позначкою «Не активний» (не ховається).
* **Блокування не ховає вас зі списків пошуку.** Правила не вміють фільтрувати результати запитів-списків, тож публічний профіль, столики й зустрічі блокувальника лишаються у стрічках, які отримує заблокований (вони відкриваються лише як дані списку: за id профіль уже недоступний, приєднатися не вийде). Повне приховування потребує серверного компонента, наприклад Cloud Function, що будує вибірку «навколо мене» з урахуванням блоків, або геозапитів через власний сервіс. У спільній групі, де ви обидва учасники, блок не відсікає повідомлення: це спільний простір, і засіб там — вийти з нього.
* Заблокований не бачить відмови: його застосунок показує повідомлення як надіслане. Це навмисно, щоб він не дізнавався про блок.
* Кожна захищена блоком дія коштує додаткове читання документа (до 9 для створення групи).
* **Push-сповіщення розкривають Expo та Apple/Google імʼя відправника і id чату.** Текст повідомлень у пуші немає. Функція не надсилає пуші тим, хто заблокував відправника.
* Токен пристрою привʼязаний до телефону, а не до акаунта: коли хтось інший входить на тому ж телефоні, документ `devices/{id}` переходить до нього. Під час виходу пристрій видаляється; якщо мережі не було (3 с), старий власник отримуватиме пуші, доки телефон не перейде до іншого акаунта або Expo не повідомить `DeviceNotRegistered` (тоді функція сама видаляє запис).

## Розгортання

1. **Firebase Console → Authentication → Sign-in method:** увімкніть **Email/Password**. Вимкніть Anonymous.
2. **Authentication → Templates:** налаштуйте лист підтвердження email українською.
3. **Authentication → Settings → Authorized domains:** лишіть лише потрібні.
4. **Google Cloud Console → Credentials:** обмежте Web API key (Android/iOS-застосунки за bundle id та SHA-1). Ключ `FIREBASE_API_KEY` не секрет, але без обмежень ним можна зловживати.
5. Задеплойте правила (вони містять і `devices` для push; Cloud Function див. у README) (**після** кроку 1, інакше застосунок не зможе увійти):
   ```bash
   npx firebase-tools@15.32.1 deploy --only firestore:rules --project <project-id>
   ```
   `firebase.json` уже вказує на іменовану базу даних проєкту.
6. Увімкніть **App Check** (Firestore → enforce) після додавання провайдера в застосунок.

> Увага: нові правила несумісні зі старими даними: `chats` без `members` і `group_meetups` з масивом `participants` стануть недоступними. Це очікувано для застосунку, що ще не випущений; для робочої бази потрібна міграція.

## Перевірка

```bash
npm test              # юніт-тести (без мережі)
npm run test:rules    # правила + контракт клієнта на емуляторі Firestore (потрібна Java 11+)
```

`test:rules` запускає **справжній код клієнта** проти емулятора з **справжніми правилами**, тому розбіжність між тим, що надсилає застосунок, і тим, що дозволяють правила, ловиться автоматично. CI виконує обидва набори.
