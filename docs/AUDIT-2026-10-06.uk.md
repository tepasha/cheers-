## Висновок

Застосунок має придатну основу для розвитку: Expo, TypeScript strict, React Navigation, Redux Toolkit, розділення UI / логіки / сервісів, тести контрактів Firestore і CI. Основна проблема готовності до релізу — узгодженість локального стану з сервером та ізоляція асинхронних операцій між сесіями. Перед широким запуском рекомендую усунути P1, підтвердити правила на емуляторі та пройти нативні сценарії на двох пристроях.

P1 — високий пріоритет: приватність, втрата/змішування даних або порушення основного сценарію. P2 — наступний етап стабілізації. P3 — розвиток UX і підтримуваності. Пріоритети є оцінкою впливу цього аудиту, а не CVSS.

## Сильні сторони, які варто зберегти

- Чисті бізнес-функції винесені в `src/logic`; побічні ефекти — у thunks/services.
- Є strict TypeScript і типізовані маршрути навігації.
- Firestore має default deny, перевірку власника, учасників чатів і серверного часу повідомлень. Email і дата народження відокремлені від публічного профілю.
- Блокування частково забезпечене правилами сервера, а не лише приховуванням у UI.
- Native Redux cache шифрується випадковим AES-GCM ключем із SecureStore; split storage зменшує кількість повторних записів.
- Чати обмежують локальний кеш 100 повідомленнями; discovery використовує geohash queries, memoized selectors і memoized картки.
- Є ErrorBoundary, валідація частини cloud payloads і захист snapshot callbacks.
- CI включає lint, unit tests, Firestore emulator tests, Android Metro export, native prebuild і компіляцію functions. Release workflows мають окремі перевірки конфігурації; OTA використовує runtime fingerprint.
- Google/Apple login і видалення акаунта вже реалізовані; server push не містить тексту повідомлення. Документація чесно описує обмеження шифрування й геоприватності.

## Деталі та варіанти виправлень

### A01. Ізоляція асинхронних операцій між акаунтами

**Де:** [favorites thunk](../src/store/thunks/favorites.ts#L30), [inbox thunk](../src/store/thunks/inbox.ts#L15), [blocks sync](../src/store/thunks/safety.ts#L56), [cloud hooks](../src/hooks/useCloudSync.ts#L30).

`restoreFavoritesFromCloud` захоплює стан A, чекає мережу і без перевірки поточного власника dispatch-ить результат. `personalDataReset` під час входу B не скасовує цей Promise. Аналогічна відсутність перевірки є в inbox та blocks sync; unsubscribe не скасовує вже запущену async обробку snapshot.

**Варіант:** додати `sessionGeneration`/request token і `ownerId` до результатів. Після кожного await та перед dispatch перевіряти актуальну сесію; reducers також повинні відхиляти чужого owner. Cleanup listener має інвалідувати запущені callbacks. В `handleFirebaseUser` вже є перевірка uid для private profile — поширити цей підхід.

**Критерій:** контрольована затримка A → logout → login B → відповідь A не змінює дані B і не створює повідомлень/сповіщень від імені B.

### A02. Підтвердження операцій, офлайн і черга відправки

**Де:** [message thunk](../src/store/thunks/social.ts#L34), [message service](../src/services/firestoreSyncService.ts#L437), [private profile service](../src/services/firestoreSyncService.ts#L109), [hangout join](../src/services/firestoreSyncService.ts#L336), [meetup thunks](../src/store/thunks/meetups.ts#L25).

Локальний optimistic update часто виконується до серверного підтвердження. Сервіси ловлять помилки та повертають void, null або `{success:false}`; UI не отримує стану failed. Наприклад, запис дати народження може не вдатися, але `submitBirthDate` усе одно відкриє основний застосунок. Join/close/збереження зустрічі можуть залишитись лише локально. Для chats немає персистентної черги, що повторно відправить невдале повідомлення після перезапуску. Redux cache зберігає UI, а не незавершені мережеві операції. Firebase JS SDK у RN не має Firestore disk persistence — це підтверджує [Firebase](https://firebase.google.com/docs/web/environments-js-sdk).

`SECURITY.md` прямо описує приховування відмови через блокування як свідоме рішення. Це не виправдовує однакову обробку network errors, invalid data і quota errors.

**Варіант:** typed `Result` або винятки до thunk; стани `queued/sending/sent/failed`, явний повтор і rollback. Для важливих записів — persisted outbox з ownerId, стабільним operationId і ідемпотентною серверною обробкою. Рішення щодо повідомлень заблокованому користувачу відокремити від інших помилок.

**Критерій:** airplane mode + перезапуск, permission-denied і full table дають передбачуваний стан, а не неправдивий успіх. Дата народження підтверджується тільки після успішного збереження.

### A03. Місткість, статуси та конкурентні зміни зустрічей

**Де:** [joinMeetup](../src/logic/meetups.ts#L100), [participation rule](../firestore.rules#L214), [seat join rule](../firestore.rules#L152), [saveMeetup](../src/services/firestoreSyncService.ts#L385).

Існуючий запрошений учасник переводиться в going до перевірки місткості: виконання підтвердило `3/2`. Правила `isOwnParticipation` не перевіряють кількість going, загальний schema limit, статус cancelled/past або строк зустрічі. Два клієнти можуть одночасно взяти останнє місце. Для hangout місткість захищена, але `isSeatJoin` не перевіряє active/expiry. Host save/cancel переписує весь meetup разом зі старою мапою participants, тому здатен затерти щойно зроблений join.

**Варіант:** atomic server join через transaction з active/status/capacity checks і лічильником confirmedCount. Заборонити прямі неконтрольовані зміни цього лічильника правилами. Для host edits — update тільки змінених полів або transaction. Запрошення не повинно обходити місткість.

**Критерій:** два паралельні join на останнє місце — один успіх; запрошений теж дотримується ліміту; cancelled/expired не приймають нових going; host edit не втрачає concurrent join. Залишення/відхилення після завершення слід дозволяти окремо.

### A04. Обхід reauthentication перед видаленням

**Де:** [private rules](../firestore.rules#L89), [hasCompletedSignUp](../functions/src/deps.ts#L89), [deleteAccount](../functions/src/account.ts#L49).

За статичним аналізом власник може видалити або переписати `users/{uid}/private/profile` без birthDate. Після цього `hasCompletedSignUp` поверне false і callable пропустить перевірку свіжого входу навіть для раніше завершеного акаунта. Потрібна вже чинна сесія цього акаунта; це не доступ стороннього без авторизації. Проблема порушує заявлену гарантію захисту від видалення через залишений розблокований телефон. Емуляторне відтворення цього ланцюжка не виконане.

**Варіант:** server-owned незворотний onboarding marker; без recent login дозволяти видалення тільки серверно підтвердженої незавершеної реєстрації. Приватний редагований документ не повинен визначати цей виняток.

**Критерій:** стара сесія завершеного акаунта не може обійти recent-login через delete/overwrite private profile. Неповна реєстрація має окремий контрольований шлях відмови за віком.

### A05. Геоблокування

**Де:** [геоперевірка](../src/services/i18nService.ts#L72), [app gate](../src/store/selectors.ts#L19), [RootNavigator](../src/navigation/RootNavigator.tsx#L93), [App lifecycle](../src/hooks/useAppLifecycle.ts#L196).

Bounding boxes не відповідають кордонам: точка `51.5,33.5` блокується як РФ. Таймзона теж не доводить фізичне місце. Крім того, геоблок перемикає тільки UI: `selectCanUseApp` не враховує geoBlocked, тому `AppShell` продовжує cloud hooks для авторизованого повнолітнього користувача. Пресети місця доступні у звичайному застосунку, геоперевірка використовує їх як координати.

**Варіант:** відокремити browse location від device location; використовувати перевірені полігони/визначення країни та обробляти невизначеність. Якщо правило є обов’язковою продуктовою вимогою, включити його в центральний gate для IO та відповідний server access flow. Не називати клієнтський екран «блокуванням на рівні протоколу».

**Критерій:** прикордонні точки України й сусідніх держав, користувач з іншою таймзоною та denied GPS мають коректний результат; blocked session не читає/публікує community data.

### A06. Геоприватність і discovery після блокування

**Де:** [precision](../src/logic/privacy.ts#L6), [public list rule](../firestore.rules#L82), [profile publishing](../src/hooks/useCloudSync.ts#L93).

Координати публікуються з точністю приблизно 14–22 м. Будь-який verified account може запитувати список users та довільні geohash ranges; радіус 3 км — клієнтська поведінка. Блокування забороняє profile get, але не list: заблокований може отримати публічне місце людини зі списку. Це чесно задокументовано, проте залишається суттєвим продуктовим ризиком для зустрічей із незнайомцями.

**Варіанти:** 200–500 м або район замість точки; явна опція видимості та пауза discovery; точне місце тільки в погодженій зустрічі. Для повного приховування від заблокованих — server discovery з обмеженнями запитів і закритим прямим list.

**Критерій:** blocked caller не отримує координати через discovery; вимкнення видимості реально припиняє публікацію/видачу профілю. Точність і декларації даних узгоджені.

### A07. Push після logout і гарантії доставки

**Де:** [releaseDevice](../src/store/thunks/push.ts#L47), [push backend](../functions/src/push.ts#L133), [Expo sender](../functions/src/expo.ts#L9), [message trigger](../functions/src/index.ts#L40).

Через 3 секунди `releaseDevice` завершується навіть без видалення server document; локальний token уже очищений. Старий акаунт може продовжувати надсилати push на цей телефон. Перехід токена до B відбудеться тільки при успішній реєстрації B; opt-out не гарантує переприв’язки. Фонова push містить ім’я автора. Це також описано в SECURITY.md.

Backend читає tickets, але не перевіряє receipts, не зберігає delivery job і не дедуплікує Firestore events. `fetch` не має власного timeout/backoff. Expo ticket означає прийняття запиту, а не доставку на пристрій; [Expo рекомендує перевіряти receipts](https://docs.expo.dev/push-notifications/sending-notifications/). [Firestore triggers](https://firebase.google.com/docs/functions/firestore-events) можуть повторно доставляти подію.

**Варіант:** lifecycle devices з коротким server lease/expiry, безпечне очищення або переприв’язка installation при вході, owner guards і персистентний стан невдалого unregister. Для backend — idempotent jobs на messageId/eventId, retry policy, receipts worker і видалення невалідних tokens. Lease обмежує час ризику, але не дає миттєвої серверної інвалідації офлайн.

**Критерій:** logout offline → login B з push off не показує B нові повідомлення A; replay event не множить push; помилки receipts видимі в telemetry.

### A08. Видалення й анонімізація кешованих даних

**Де:** [server cleanup](../functions/src/deps.ts#L95), [messagesReceived](../src/store/slices/chatsSlice.ts#L140), [DM inbox merge](../src/store/slices/chatsSlice.ts#L92).

Backend прибирає profile entry і senderName/senderAvatar. Reducer для існуючого повідомлення оновлює лише ciphertext і delivery flags, тому вже кешоване ім’я залишається — підтверджено виконанням. DM buddy теж не оновлюється з нового cloud profile. Snapshot друзів у підколекціях інших користувачів не проходить server cleanup. Account deletion збирає всі messages/writes у пам’ять; для великої історії 300 секунд може не вистачити. Membership uid залишається в chats, а group owner після видалення не має наступника.

**Варіант:** deleted-user tombstone і централізований resolver identity, merge полів анонімізації, очищення denormalized snapshots або мінімізація копій. Великі deletion jobs — посторінково, з progress/idempotency та server-owned deletion state, що припиняє нові записи; визначити transfer/archive для груп.

**Критерій:** після видалення A на B старі відкриті й повторно відкриті чати/друзі показують видаленого користувача без колишніх identity fields; interrupted deletion поновлюється без пропусків. Текст повідомлень має окрему задокументовану retention policy.

### A12. Модель шифрування

**Де:** [key derivation](../src/services/cryptoService.ts#L24), [fingerprint](../src/services/cryptoService.ts#L107), [security UI](../src/screens/ChatRoomScreen.tsx#L388).

Ключ виводиться з bundle constant і public chatId. Кожен, хто має ciphertext і застосунок, може його відтворити; encryption не забезпечує незалежний секрет від backend/експорту бази. Firestore rules залишаються реальною межею доступу. Коментарі, SECURITY.md та UI вже чесно зазначають, що це не E2EE. Fingerprint є простим 32-bit hash, а не доказом тотожності ключів/учасників.

**Варіанти:** для MVP — зафіксувати threat model і прибрати fingerprint, який не дає заявленої перевірки. Якщо приватність листування є головною обіцянкою продукту — обрати перевірений протокол/SDK для per-device keys, key exchange, verification, rotation і multi-device recovery. Саме додавання X25519 без протоколу не вирішує E2EE.

**Критерій:** гарантії UI/документів відповідають threat model; для E2EE backend із DB dump не може отримати ключі. Перед E2EE релізом потрібна окрема перевірка протоколу.

### A13. Порядок та історія повідомлень

**Де:** [chat stream](../src/services/firestoreSyncService.ts#L610), [message merge](../src/store/slices/chatsSlice.ts#L129).

Stream сортує лише змінені документи; reducer дописує їх до наявного масиву без загального server order. Старі повідомлення можуть опинитися після нового optimistic message і замінити preview. Server createdAt видаляється з DTO перед reducer. Підписка і кеш обмежені 100, а load older відсутній; користувач не може отримати решту збереженої розмови.

**Варіант:** зберігати serverCreatedAt/clientCreatedAt, нормалізувати за messageId, впорядковувати весь loaded window; optimistic order має бути узгодженим. Додати cursor pagination для older pages і відокремити streamed tail від loaded history.

**Критерій:** initial snapshot після локальної відправки, delayed snapshots і більше 100 messages зберігають порядок та дозволяють відкрити попередню історію.

### A14. Inbox preview та unread

**Де:** [chat preview fields](../src/services/firestoreSyncService.ts#L445), [inbox merge](../src/store/slices/chatsSlice.ts#L102), [inbox thunk](../src/store/thunks/inbox.ts#L45).

Preview updatedAt пишеться з годинника телефона. Будь-який учасник може оновити preview без створення message; DM block check стоїть на messages, але не на chat preview update. Unread збільшується на snapshot update, тому не є точною кількістю повідомлень; metadata-only зміна теж може виглядати як новина. Read state і hidden chats зберігаються лише на пристрої.

**Варіант:** server-owned preview, прив’язаний до прийнятого messageId/server timestamp; per-user read cursor (`lastReadMessageId`/sequence), явне рішення щодо sync hidden/muted. Для прямого preview update перевірити блокування та зв’язок із новим message.

**Критерій:** учасник не підміняє preview без message; один read на пристрої A коректно відображається на B, якщо це обіцяно продуктом; skewed clock не повертає старий preview.

### A15. Focus, navigation та cold push

**Де:** [useChatSync](../src/hooks/useChatSync.ts#L7), [chatOpened lifecycle](../src/screens/ChatRoomScreen.tsx#L40), [pending push](../src/hooks/useAppLifecycle.ts#L182).

Підписка існує весь час mount екрана. Native stack може залишити ChatRoom mounted під іншим екраном, але його callback продовжує позначати messages як read. `pendingChatId` очищується одразу після navReady; якщо inbox ще не завантажений, відкривається тільки список Chats. Перевірка known також не враховує видимість blocked thread.

**Варіант:** focus/AppState-aware read tracking; authoritative active route; `inboxReady` і очікування потрібного чату з timeout/fetch-by-id та access checks перед навігацією. Блокування перевіряти і для push відкриття.

**Критерій:** ChatRoom → інший екран не читає невидимі messages; cold-start push до незавантаженого чату відкриває саме чат після login/hydration. Перевірити на Android/iOS.

### A16. Масштабованість feeds та battery saver

**Де:** [hangouts query](../src/services/firestoreSyncService.ts#L269), [meetups query](../src/services/firestoreSyncService.ts#L415), [inbox query](../src/services/firestoreSyncService.ts#L587), [throttle](../src/services/firestoreSyncService.ts#L279).

Hangouts і meetups читаються глобально без geofilter/limit; inbox теж без пагінації. Nearby queries обмежені, але решта feeds росте разом з усім продуктом. Battery saver просто повертається з callback у межах throttle window: якщо після пропущеного update немає нового, остання зміна не потрапить у UI. Це не зменшує кількість Firestore reads. Query з Date.now має фіксований cutoff на момент створення; час сам не змінює query і не припиняє читання оновлень документів, що вже прострочились після підписки.

**Варіант:** geo/city partition + limit і cursors; окремий stream своїх active tables; trailing coalescing замість втрати snapshot; refresh часових queries контрольовано. Виміряти billed reads/session, CPU і battery на реальному пристрої, потім змінювати frequency.

**Критерій:** тестові тисячі чужих feeds не завантажуються кожному; останній throttled snapshot доставляється; встановлений бюджет reads/session дотримується.

### A17. Відбір nearby

**Де:** [pickNearby](../src/logic/nearby.ts#L45), [selector](../src/store/selectors.ts#L43), [range queries](../src/services/firestoreSyncService.ts#L749).

Service обирає 50 від grid center до фільтрації блоків і точної відстані від реального місця. Внаслідок цього UI може показувати менше доступних людей; 50 найближчих до grid center не гарантовано є 50 найближчими до device center. Range limit 100 за geohash також не гарантує глобально nearest results у щільній зоні. Об’єднання ranges не дедуплікує uid перед cap — це захисне вдосконалення на випадок перетину/повторів, а не доведений поточний дубль у UI. Поля online/inactive обчислюються лише при snapshots.

**Варіант:** query candidate pool → dedupe by uid → block/visibility filters → exact distance → final cap. Для щільних зон — adaptive paging або server query. Presence перевираховувати за таймером/clock bucket без повторних мережевих reads.

**Критерій:** fixtures зі зміщеним grid center, blocked nearest profiles і щільною зоною дають коректний фінальний відбір та часові online status.

### A18. Синхронізація між пристроями і видалення

**Де:** [favorites restore](../src/store/thunks/favorites.ts#L30), [blocks sync](../src/store/thunks/safety.ts#L56), [meetups merge](../src/store/slices/meetupsSlice.ts#L17).

Favorites merges тільки додавання; порожня cloud колекція не прибирає локальні записи. Blocks читаються один раз при запуску ефекту, тому unblock іншого пристрою не є realtime. **Критерій:** remove favorite/unblock/delete meetup на A коректно відображається на B; локальні pending зміни не губляться під час hydration.

### A24. Завершення продукту та підтримуваність

**Де:** [AuthUser/Buddy/Chat types](../src/types.ts), [filter logic](../src/logic/buddyFilters.ts#L5), [filter UI](../src/components/FilterSheet.tsx#L10), [profile editor](../src/screens/ProfileScreen.tsx#L216), [venues](../src/data/venuesData.ts#L1), [store docs](store/privacy-policy.uk.md).

- `ChatThread` моделює групу через обов’язковий buddy placeholder; `Message` — набір optional fields. Discriminated unions для DM/group і типів messages, DTO/domain/view boundaries та runtime schemas зроблять невалідні стани важчими для створення. `getFriendsFromFirestore(): Promise<any[]>` і вимкнений `no-explicit-any` послаблюють strict.
- `firestoreSyncService.ts` об’єднує багато незалежних доменів. Розділити auth/profile/chat/meetup/safety repositories зі спільною політикою errors, owner guards і diagnostics. Redux Toolkit, navigation і UI-kit можна розвивати в поточному стеку.
- Store documents містять `[email]`, `[НАЗВА]`, `[дата]`, `[N]`, `[строк]` та редакторські примітки. Це чернетки, не готові публічні materials. Завершити дані, retention, deletion flow для Apple і публікацію доступних URL; actual store/privacy settings не перевірялися. Перед заявами про відповідність політикам потрібна окрема перевірка актуальних вимог і фінальних матеріалів.

**Критерій:** анкета реально впливає на пошук; фільтр і результати узгоджені; мови коректні після перемикання; користувач бачить loading/error/empty; store links ведуть до завершених сторінок.

## Варіанти вдосконалення

| Варіант | Обсяг | Коли обирати | Результат |
| --- | --- | --- | --- |
| A. Стабілізація поточного MVP | A01–A08, критичні async/profile/history fixes, розбір A09, правила та device regression tests | Потрібна контрольована beta | Надійні основні сценарії, відома і задокументована модель приватності |
| B. Основа для росту — рекомендований | A + owner-scoped hydration/outbox, transactional backend commands, pagination/geo feeds, telemetry, moderation, migrations і profile onboarding | Планується публічний запуск | Передбачувана синхронізація, контроль витрат і можливість підтримувати користувачів |
| C. Приватність листування як ключова властивість | B + перевірений E2EE protocol/SDK, per-device identity, recovery/rotation, приватний discovery | Приватність є головною обіцянкою продукту | Інша модель ключів і доступу, що потребує окремого проєктування й security review |

Практичний порядок: спершу session guards і error contracts → серверні операції join/delete → profile hydration та outbox → порядок/пагінація chat → push lifecycle/receipts → приватний discovery → telemetry/moderation → UX/типи/оптимізації. Перехід на native Firebase SDK варто оцінити, якщо потрібні нативний offline cache/App Check/Crashlytics: він додає native build/migration роботу; для поточного JS SDK можна реалізувати власну надійну синхронізацію.

## Умови завершення стабілізації

1. Нові regression tests відтворюють і закривають шість підтверджених дефектів.
2. Firestore rules проходять існуючий suite і нові негативні сценарії direct API, expired/full joins, reauth bypass та preview spoofing.
3. Два реальні пристрої підтверджують account switch, міжпристроєву синхронізацію, offline/restart, block/delete і cold push.
4. Preview/production builds перевірені Gradle/Xcode, а sign-in, Maps і push — з реальними конфігураціями.
5. Security guarantees, privacy options і завершені store materials відповідають фактичній поведінці.
6. Є baseline startup, memory/FPS, battery, reads/session і error rates; оптимізації порівнюються з ним.

## Межі цього аудиту

Нативний runtime, візуальний дизайн на пристроях, доступність для screen readers, battery/FPS, production Firebase rules/deployment, реальні OAuth credentials, доставка push і production store settings не перевірялися. Висновки про runtime-проблеми позначені окремо від статичного аналізу та продуктових рекомендацій. Запуск тестів і export не доводить відсутності інших дефектів; нові зміни робочого дерева можуть вимагати повторної перевірки відповідних ділянок.
